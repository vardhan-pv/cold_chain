# Machine Learning Implementation and Evidence

Both estimators are real trained models: XGBoost and scikit-learn Random Forest. The predictor loads them, checks the artifact hashes and feature schema, and calls their probability inference methods. No percentage is hard-coded as an ML result. Missing artifacts or invalid required sensors produce a null probability and an explicit unavailable/invalid status.

## Data provenance

No measured cold-chain dataset was uploaded. The supplied dataset is therefore marked `SIMULATED_DATA`, generated by the seeded illustrative plant in `simulator/engine.py`. The plant has not been calibrated against the future Peltier enclosure. It is useful for testing software integration, not proving field predictive accuracy.

The dataset has 120 complete episodes and 10,800 rows. Eight episodes per scenario group form training, two validation, and two testing. The split contains 7,200 training rows, 1,800 validation rows, and 1,800 test rows. Episodes never cross split boundaries. A duplicate normal scenario group increases healthy examples deliberately. Labels describe the active simulated fault condition and are excluded from inference features.

When measured data exists, label it `MEASURED_DATA`; separately generated augmentation should be marked `SYNTHETIC_DATA`. Do not simply rename the current simulation file. The default training command intentionally generates the documented simulated experiment. `python -m ml.train_measured labelled_runs.jsonl --output ml/measured_models` implements the separate measured-log path. It requires canonical HARDWARE telemetry, a reviewed binary label, evidence text and a split on each line; chronological, disjoint boot groups prevent leakage. Simulation inputs, duplicate sample identities and split overlap are rejected. Importer and estimator tests use clearly identified software fixtures, not hardware evidence. No measured model is supplied.

## Feature construction

`feature_engineering.py` uses the current record and at most 60 seconds of past readings from the same device, mode, and boot. Features include temperature, humidity, primary current, door state/duration, reported output states, thermal difference, temperature rate, rolling means/standard deviation, and primary current ratio. There is no pressure, vibration, backup-current, scenario-name, label, or future-reading input.

The train and serve paths call the same feature function. Tree models do not require a fitted standardization scaler, so a meaningless `scaler.pkl` is not produced. Invalid required sensor readings prevent inference; they are not replaced with plausible measurements.

## Training and model selection

XGBoost uses 90 trees, maximum depth 3, learning rate 0.08 and fixed seed 42. Random Forest uses 100 trees, depth at most 10, minimum 4 samples per leaf, balanced classes and fixed seed 42. The validation F1 scores determine the estimator weights. A validation-only threshold search selects the ensemble decision threshold. Test labels never select weights or thresholds.

The saved manifest contains model version, feature version, dataset hash, artifact hashes, library versions, split episode identifiers, class counts, confusion matrices, precision, recall, F1 and ROC-AUC. The dashboard displays these actual saved results with simulation provenance. The exact metric values are in `trained_models/manifest.json`; use the delivered version rather than copying old results after retraining.

This baseline classifies the present anomalous condition. It does not establish lead time before failure, predict remaining useful life, or validate cargo spoilage. Measured failure onset labels, temporal holdouts, operational false-alarm analysis, probability calibration and out-of-distribution assessment remain necessary.

## Control use

The backend can use ensemble risk to raise an advisory warning. Confirmed primary-fault transitions require sustained electrical or thermal evidence, or an explicitly labelled fault injection. Critical current, temperature and sensor-invalid rules outrank ML. The ESP32 adapter runs deterministic safety rules and can display an expiring backend risk advisory; on-device XGBoost/RF conversion, memory limits and inference latency are pending.

Load only the trusted joblib artifact generated for this project. XGBoost uses its JSON model format. A checksum verifies local consistency but is not a signature proving trust in an externally supplied model.

## Labelled JSONL input

Each line contains exactly `split` (`train`, `validation`, or `test`), `label` (integer 0 or 1), `evidence` (a reviewed observation reference), and `telemetry` (one complete canonical payload). Use payloads from a hardware telemetry export and annotate them from actual observed conditions. Each device/boot is one episode. Entire training runs must precede validation runs, which must precede test runs. Every split must contain both normal and anomalous examples. Invalid sensor records are excluded and counted, never filled with invented measurements. The saved manifest retains the input hash and counts. Operator-supplied provenance is not independently certified by the importer.
